// ELI5 · SCENE IMAGE GATE

Two flags.
Four outcomes.
One trap.

The P4 image gate has an on switch on the server and an on switch in the browser bundle. Three of the four combinations are fine. The fourth arms the only half that can stop a run.

// EVERY COMBINATION

What each setting actually does

VITE_IMAGE_GATE_ENABLED
IMAGE_GATE_ENABLED
Both off · safe

Nothing runs. Scene images behave exactly as they did before P4 shipped. This is the default.

VITE_IMAGE_GATE_ENABLED
IMAGE_GATE_ENABLED
Server only · safe

The server is ready and nobody ever calls it. The browser never wires the checks up, so the server flag is simply unread. Harmless.

VITE_IMAGE_GATE_ENABLED
IMAGE_GATE_ENABLED
Client only · the trap

The browser wires up both checks. The strict one runs locally and hard-flags scenes and spends rerolls. The forgiving one hits the server, gets a 503, and is silently swallowed. You get the punishing half with none of the judgement.

VITE_IMAGE_GATE_ENABLED
IMAGE_GATE_ENABLED
Both on · the real gate

Both halves run. This is the only setting the gate was designed and smoke-tested for. Set both or neither.

// WHY IT BITES

One gate, two halves,
opposite severity

People assume a half-on feature flag gives you a gentler version of the feature. Here it gives you the harsher one.

Half A · deterministic

checkSceneImage

  • Runs in the browser. Never touches the server, so the server flag cannot switch it off.
  • Fails a scene, then rerolls it once. That reroll is a real image generation, billed.
  • Still failing, it sets status = flagged and returns. That scene is now blocked from approval.
Half B · the AI gate

imageGateCheck

  • Calls the server, which is where IMAGE_GATE_ENABLED is finally read.
  • Flag only. It records a verdict and never changes status, so it cannot block anything.
  • Fails open by design. A 503, a timeout, a parse error: all swallowed, run continues.

Both halves are handed out together by one function, gateDepsFor, from one flag: the client one. Only Half B ever asks the server for permission. That is the whole bug in one sentence.

// THE RULE

Set both, or set neither.

And remember which one is which: IMAGE_GATE_ENABLED is read at runtime, so flipping it takes effect immediately. VITE_IMAGE_GATE_ENABLED is baked into the bundle at build time. Changing it on Vercel does nothing at all until you redeploy, which is exactly how a deploy drifts into the trap state without anyone touching the server.
